# Native marker regression helper

## Repeatable all-mode performance matrix runner

From the repository root, produce a plan without calling adb:

```powershell
powershell -NoProfile -File scripts/android/performance-matrix.ps1 -Scenario all
```

The default writes only a `matrix-report.json` plan under `.openai/performance-matrix/`; every case is `NOT_RUN`. To perform the opt-in, read-only collection, the device owner must explicitly pass `-Capture -Serial <serial>`. The script does not install/start/stop apps, clear/reset state, inject input, or change map settings. It records point-in-time `dumpsys cpuinfo`, package `meminfo`, `gfxinfo framestats`, and raw `ps -A` process lists before and after each input window. The process list is retained for reviewer attribution of WebView renderer processes; the runner does not label app-process CPU as whole-device gain. `cpuinfo` is a system snapshot, not per-process elapsed CPU.

Scenario IDs can be selected with `-Scenario single-2d,dual-diff-3d`; `-Adb`, `-Package`, `-OutputDirectory`, `-FixtureRoot`, and `-WindowSeconds` are configurable. By default the runner waits for Enter at manual boundaries. A positive `-WindowSeconds` instead records process counters, waits a fixed number of seconds without touching the UI, then records them again; the operator controls the independent UI window. It is an observation window, not automated input. Fixture names, task branches and explicit gaps are listed per case in the JSON report. A fixture file's presence only changes `fixturePresent`; it does not assert fixture correctness or mark a scenario as passed. The runner refuses to use an output directory containing a previous report or other files, preserving A/B evidence. Inspect and reset only QA-owned fixtures under the existing QA procedure; preserve user markers, routes, drafts, caches and settings.

The matrix includes single-map 2D/3D, same-source and different-source dual-map 2D/3D, zoom levels 6/9/12/15, QA-draft drawing/editing, route display, a separate navigation-active render-state branch, recording-in-progress and paused branches, measurement-picking, section-profile, 100-marker density, panel toggles, and dual-map exit/single-map restoration. Navigation-active requires a QA route with finite synthetic `navigationProgress`; it injects no GPS and is not real positioning acceptance. Recording fixtures also require QA-only state and no GPS; they do not start the native recording service. These fixtures are not implemented or bundled. Every scenario lists its render/task branch, required fixture, and current fixture gap. The matrix is an execution plan, not an acceptance result; each input window and starting fixture still needs independent review.

### Metric boundaries

- The existing `Native163PerfProbe` is a separate interactive-preview QA probe. It can sample actual frame counts and allowlisted map/cache counters. Its optimized SDK frame hook reports unavailable, so SDK prepare duration and actual map FPS are not currently supplied by that hook. Do not derive either from frame counts without validated timed deltas. Its stack sampling is explicitly perturbative and disabled for timing runs.
- `gfxinfo framestats` and the probe's Android `Window.FrameMetrics` describe Android Window/HWUI, not the map's `GLSurfaceView` FPS. This runner does not collect WebView/page timing; WebView metrics, if collected separately, must remain separately labeled.
- SDK prepare durations, WorldWind frame counts, Android Window/HWUI frame metrics, WebView/page metrics, system CPU snapshots and memory snapshots are separate evidence. The runner does not claim an actual map FPS value.
- Per-process CPU snapshots read the already-running target's `/proc/PID/stat` user/system tick counters and `/proc/uptime`. Access is probed at runtime because Android shell/SELinux permissions vary. Permission denial, absent PID, changed PID or changed process start time is retained as an explicit unavailable/non-comparable result; no improvement percentage is computed. Raw `ps -A` before/after logs include renderer process names for separate review.
- There is no automatic PASS: fixtures, app mode, gesture window, metric availability, repeat count and visual/functional behavior must be checked by the reviewer. No dense-marker, saved-draft or navigation fixture is generated by this runner.

`tests/android-performance-matrix.test.mjs` executes dry-run behavior checks for matrix branches, missing fixtures, fixed-window planning, invalid scenarios, and non-overwrite protection. It does not contact a device; target `/proc` permissions remain unverified until an explicit Capture run.

This Java Instrumentation helper targets the existing private release package
`com.guanyun.weather.shantu.preview`. It does not build or modify that application APK and
does not use WebView debugging/CDP. The helper's package/class/environment names retain the
historical `qa149` / `Native149Instrumentation` identifier; that legacy tooling name is not
the version of the target application.

## Reversible cache-scope isolation (dedicated simulator only)

`native163-cache-scope` is an Instrumentation-only mode before this helper calls
`attachTarget` or `startActivitySync`; it calls neither. It requires the platform `Application`, no live Activity, no `GLThread`, and
no known map tile/snap worker threads. If the safety check is unavailable or an app/map thread
is active, it refuses to move anything. Only two fixed sibling directories are in scope:
`files/shantu-map-browse-cache` and `cache/shantu-native-map-tiles`.

Use a new session ID containing only ASCII letters, digits, `_` or `-` (1–48 characters):
the MuMu3 image spoofs a phone model, so its adb serial must first be matched on the host to
the dedicated MuMu3 instance. Only after that host-side check, add
`-e confirmedDedicatedEmulator true`; the helper also requires `Build.SUPPORTED_ABIS` to contain
`x86_64`. This flag is not for a physical phone and must not be passed there.

```powershell
adb -s <verified-mumu3-serial> shell am instrument -w -e mode native163-cache-scope -e confirmedDedicatedEmulator true -e action isolate -e sessionId coldA com.shantu.qa149/com.shantu.qa149.Native149Instrumentation
# Run the isolated cold-cache QA flow, then stop/close the target app before restoring.
adb -s <verified-mumu3-serial> shell am instrument -w -e mode native163-cache-scope -e confirmedDedicatedEmulator true -e action restore -e sessionId coldA com.shantu.qa149/com.shantu.qa149.Native149Instrumentation
```

Existing directories are renamed to sibling `.qa-isolated-<sessionId>` names. A line-oriented,
recoverable manifest is kept under the target app's private external Documents directory; it
records only the two fixed labels, initial existence, direct-child counts, session, and state.
Restore returns original directories and renames any newly generated caches to
`.qa-generated-<sessionId>` so neither set is removed. Missing original directories remain
missing after restore. Reusing a session with an existing manifest is refused. The report emits
only state/counts; it never enumerates tile names or reads tile contents, URLs, keys, records,
offline data, or WebView storage. Review the helper and the manifest before running; do not run
this mode on a production phone or while the map is open.

## Optional short thread-stack diagnosis

The interactive socket accepts `{"action":"perf-start","stackSampling":true}`.
Ordinary `perf-start` keeps this option off. The extra daemon samples main/GLThread
stacks with a 50 ms fixed delay, at most 1,200 samples or 60 seconds, and reports
capture/write work, approximate missed intervals, errors and stop reason in the
existing private JSONL and `perf-snapshot`/`perf-stop` result. At most four threads
and 32 frames per thread are retained. These are diagnostic stacks, not FPS.
Stack capture can pause or otherwise perturb the target; turn it off for timing
comparisons. In the 163 follow-up it averaged 16.11 ms of work per capture, so the
sampled run is used for call-path attribution only. Do not publish raw dumps or
coordinates. This helper does not change the production APK or its settings.

## Modes

The interactive-only `vector-diagnostic-mask` action accepts `mode: all | no-labels | none`.
It temporarily changes the four cartography MVT layers' enabled flags on the main thread,
retaining their original values by object identity. `all` restores those original values;
it does not enable a layer that was originally disabled. Responses report each original/current
flag and the snapshot cost. `vector-traversal-snapshot` also reports `enabled` so a run can
detect a later business-state update overriding the diagnostic mask. Errors fail the command.
Use only on the dedicated simulator, restore `all` in the test's `finally`, and restart the
target from its saved fixture when finished. No business settings, raw tile cache or user data
are changed. Disabled-layer runs are attribution experiments, never a product fix or visual
acceptance. Wait for both maps to settle and keep method/stack sampling and video off for timing.
The helper calls each actual WorldWindow's retained `requestRedraw` method; optimized builds
may remove the global WorldWind static convenience method, so reflecting that method is unsafe.

- `inspect`: read-only activity, map, camera, source ID, annotation-count, selection-ID, and
  visible-control inspection.
- `raster-diagnostics`: read-only native camera/cache/network counter sampling over long-far
  tilt and bearing stages. It takes only first/last screenshots per stage, records one-second
  camera and allowlisted numeric diagnostic snapshots, includes target package/versionCode,
  and restores the exact starting camera in `finally`. It does not add markers or edit
  annotation storage. Diagnostic output excludes URL, host, path, source, key, and token
  fields; if the guarded host inspection method is unavailable, the report records that
  limitation without substituting synthetic frames or network requests.
- `native-regression`: temporarily appends three UUID-based QA pins through the target app's
  real WebView storage events; waits for the actual native screenshot to show all three pin
  colors; sends touchscreen MotionEvents; checks actual GPU pick IDs and selected IDs;
  exercises rapid alternation, blank clearing, camera zoom thresholds, and poses.
- `native-regression -e pickOnly true`: runs the pick/clear flow and skips zoom/pose sweeps.
- `native-regression -e followUp true`: runs the UI follow-up flow, including real MotionEvent
  taps on the selection card's start/end buttons, verifies the route input values, returns to
  the map, reselects QA-A, and captures five camera poses. It skips rapid alternation and the
  full zoom sweep. It never requests route calculation or search.

The QA records use unique IDs, are appended without replacing existing annotation records,
and only this run's IDs are removed. Before removal, a QA selection is cleared using the
visible “完成调整” button through its DOM rectangle and a real touchscreen event. The original
camera is restored in `finally`. If the process is force-stopped, inspect the `qa149-*` IDs in
`guanyun.annotations.v1` before any manual cleanup; do not clear application data.

Evidence screenshots and a JSON report are written to the target application's app-specific
external pictures directory. They include actual camera/selection snapshots, picker results,
timings, and rendered-pin color counts. These helper outputs are diagnostic evidence; review
the native screenshots before making a visual acceptance claim. No map-source URLs, API keys,
or credentials are read or emitted.

## 160 drawing and line diagnostics

The `interactive-preview` loopback bridge also accepts the fixed actions
`telemetry-start`, `telemetry-snapshot`, `telemetry-stop`, and `snap-targets`.
It does not accept JavaScript, a URL, or a script path from the caller.
Telemetry is bounded to 100 samples; it reports input-to-SVG attribute timing,
capture dimensions/duration/encoded length, and actual magnifier `drawImage`
counts. These are not application FPS or end-to-end latency. It never saves
capture data URLs, geographic positions, route contents, or map credentials.
`snap-targets` only projects cached real MVT geometry to screen coordinates;
it neither fetches data nor commits a drawing. Use an empty QA-owned draft and
undo only the points added by the test.

Generate synthetic renderer-only line fixtures from the repository root:

```powershell
node scripts/android/native-marker-regression/create-line160-fixtures.mjs
```

An optional `longitude,latitude` argument chooses a public test origin. The
default `0,0` exposes a currently unresolved tilted-camera round-trip deviation;
retain that failure separately from successful loaded-ground checks. These
fixtures never inject GPS or recording positions. Push the generated JSON to
the target application's external files root, then use
`-e mode line-position-regression -e fixtureFile qa-line-position.json`.
`fixtureVersion:160` (legacy schema name) and every positive `expectedStrokeScale` no greater than 1 are mandatory; 161 far-zoom fixtures include 0.12. Assertions
retain the requested scale; they do not silently substitute the actual camera
scale when the requested pose fails. `cameraProbe` may report unavailable fields
after R8 optimization and must not be interpreted as successful measurement.

`restore-qa-viewport` reads a canonical external-files JSON filename with the
explicit purpose `restore-native160-qa-view` and a validated camera. It restores
only a viewport displaced by QA, with no GPS or saved-record write. Do not use
it to replace a user's active camera without a snapshot from that QA session.

## Build the helper only

From the repository root:

```powershell
powershell -NoProfile -File 'scripts\android\native-marker-regression\build.ps1'
```

The script uses configurable `-JdkRoot`, `-SdkRoot`, and `-ProjectRoot` parameters. If
`-ProjectRoot` is omitted, it searches parent directories for `mobile-native`. It compiles
with UTF-8/JDK 17/Android 35, signs the helper with the existing local test keystore, verifies
it, and prints its SHA-256. The private keystore is not part of this helper directory; provide
the locally held signing password through the legacy `QA149_KEYSTORE_PASSWORD` environment
variable without printing it. Build output stays beneath this directory.

## Install and run after reviewing the helper APK

Replace `<serial>` with the device serial and `<generated-build-folder>` with the generated
folder name printed by the helper build (for example, `build-<generated-id>`):

```powershell
adb -s <serial> install -r 'scripts\android\native-marker-regression\<generated-build-folder>\Native149Instrumentation.apk'
adb -s <serial> shell am instrument -w -e mode inspect com.shantu.qa149/com.shantu.qa149.Native149Instrumentation
adb -s <serial> shell am instrument -w -e mode raster-diagnostics com.shantu.qa149/com.shantu.qa149.Native149Instrumentation
adb -s <serial> shell am instrument -w -e mode native-regression com.shantu.qa149/com.shantu.qa149.Native149Instrumentation
adb -s <serial> shell am instrument -w -e mode native-regression -e pickOnly true com.shantu.qa149/com.shantu.qa149.Native149Instrumentation
adb -s <serial> shell am instrument -w -e mode native-regression -e followUp true com.shantu.qa149/com.shantu.qa149.Native149Instrumentation
```

Instrumentation output is returned under `qa149_json`. Pull only the reported target-app
evidence directory when needed; it is separate from this source tree.

## Interactive native APK preview

Use `-e mode interactive-preview` after forwarding `adb -s DEVICE forward tcp:23458 tcp:23458`. The helper keeps the actual APK open and accepts bounded real touch events on Android loopback only. Start `python preview-server.py --adb ADB_PATH --serial DEVICE --port 9174` with Python/imageio-ffmpeg available, then open the localhost preview. Current video/touch dimensions assume MuMu 1256x2760; adapt both before using another size. Only `stop` finishes the instrumentation. This is a development preview, not a product service or phone FPS result.

`-e rasterExtended true` extends `raster-diagnostics` to zoom6/10 with 35/55/75-degree poses.

## Ordinary-road density (162)

`-e mode road-density-regression -e fixtureFile qa-native162-roads.json` accepts a local `poses` array with validated camera objects. Default coverage is Chengdu zoom 8/9/10/11/12/15 and mountain 8/10/11/12/15; each pose records road-layer ON/OFF/ON PNGs, render-cut groups and parent/child overlap. Temporary vector annotation settings preserve the selected base source, and full renderState/camera/layer/contour/revision values restore in `finally`. No GPS or saved-record writes.

A separate cold near fixture may set `requireMatrixCoverage:false`, `isolation:false`, `minimumWarmupMs:10000`, and one `city-z15` pose. It avoids comparing a streaming source12 overview with source14 near detail. `captureUnsettled` and pending counts are mandatory evidence; the helper never automatically establishes visual acceptance or a fully drained network. Raw PNGs and reports stay private.


## Bounded ART method attribution (not a benchmark)

The interactive socket accepts `{"action":"method-trace-start","intervalUs":10000}` and
`{"action":"method-trace-stop"}`. Sampling intervals must be 5,000–100,000 microseconds.
The helper uses a 16 MiB buffer, requires 64 MiB available storage, saves a unique trace under
the target app's private external Documents directory, and stops after at most 30 seconds or
when the interactive session closes. This is helper-only; it is not shipped in the product.

Sampling suspends app threads and may materially change GC, scheduling and frame timing.
Use it for coarse attribution, keep the exact optimized APK's R8 mapping for method names,
and repeat timing with ART and QA periodic sampling disabled. System traces need a checked
non-overflowing buffer. Concurrent GC duration is not main-thread pause, and GL submission
is not GPU execution time. Keep raw traces private; they can contain runtime or user context.
Do not disable platform security or use this helper to turn an optimized APK into a debug build.
