# 拖动地图的临时瓦片缓存

用户希望往返拖动时保留已经看清的区域，减少同一位置反复由模糊变清晰。此轮只调整最近瓦片保留和现有浏览缓存的内存读取，不改变高清目标、相机或图源，不增加请求并发。

## 实现范围

- `modules/map/recentTileCache.ts` / `TerrainMap.tsx`：主图、双图共同使用 MapLibre 的离屏瓦片缓存，容量系数从默认5提高到8，并设每个 source 最多256张。实际容量取视口估算与上限的较小值；这是每图源限制，当前可见瓦片和其它图层的内存另计，并非整个应用只占256张。地图销毁后释放。
- `modules/mapSources/browserTileCache.ts`：在原64MiB IndexedDB浏览缓存之前加入16MiB、最多512项的内存LRU；保留原有效期和服务端缓存限制，命中返回独立副本，避免短暂往返每张都等待磁盘读。它覆盖既有自定义/坐标校正传输，普通直接URL栅格仍由MapLibre和浏览器负责，不宣称所有请求都经过此层。
- 原浏览缓存数据库、路线离线包、收藏、私人图源和天地图配置保持；临时缓存不显示为收藏夹中的新离线包。

## 定向验证

真实 Chromium + 安装的 MapLibre 6.7.0 使用本机生成256px PNG，服务端 `Cache-Control: no-store`，因此以下是引擎已解码瓦片复用，不是HTTP缓存造成。以相同中心、缩放和移动路径，对比默认配置与本轮配置。每组先移开足够远，再回到原位置。

| 手机视口 | 显示档位 | 默认回访新请求 | 本轮回访新请求 |
|---|---|---:|---:|
| 390×857 | 高清 / tileSize128 | 32 | 0 |
| 390×857 | 标准 / tileSize256 | 12 | 0 |
| 360×780 | 高清 / tileSize128 | 32 | 0 |
| 360×780 | 标准 / tileSize256 | 12 | 0 |

四组中心/缩放恢复一致，瓦片失败、取消和MapLibre错误均0。另在390×857、62°倾角、恒定0m模拟Terrarium地形下做回拖检查，影像与DEM均0新增请求、0错误。主审读取fixture实现、计数结果并查看2D/3D截图。证据在本机 `.openai/recent-tile-cache/`。测试有意覆盖旧容量不足而新容量能保留的范围；超过新上限仍会淘汰，不表示无限距离回拖都零请求。

本机返回完成时间约144–147ms，原设置327–526ms，仅说明此受控测试中复用避免了重取；不作为真实服务器、手机帧率或几倍提速承诺。真实手机GPU内存压力、长时间双图使用仍需复测。

## 边界与后续

没有看过的区域、跨越缓存上限、切换图源/重建source、改变高清级别仍可能需要新瓦片。临时缓存不能解决服务器429限流，也未加入渐进高清调度或失败瓦片重试；这些调查见 [加载策略](raster-loading-investigation-20261024.md)。本轮未用淡入动画掩盖网络等待。

已交付Mac138独立应用包保持138源码，不包含此轮临时缓存。Android139与私人预览已更新；23项定向检查、类型检查、构建及私人配置核对通过，完整边界见 [139交付](release-0.2.139.md)。

官方参数说明：[MapLibre MapOptions](https://maplibre.org/maplibre-gl-js/docs/API/type-aliases/MapOptions/#maxtilecachesize)，同时核对本机6.7.0的tile_manager实现。
