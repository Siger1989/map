目标：调查同一二维码“【推荐】超强”在奥维可显示、山兔空白，并减少地图坐标校正的计算开销。当前源码基线 ec47ec0aa5f23cba6dfa2dd576197a82b6f34efe，分支 codex/rollback-ui-0235-20260921；已有未提交 UI 工作保留。本轮没有生成新 APK、升版本、提交或推送，已交付 0.2.94 不包含以下新增修改。

- 实际二维码与原始主合集同一配置，成功解析为单层 HTTPS XYZ、GCJ02、256px、0–20 级，模板顺序 z/y/x；没有额外鉴权 query。没有修改源声明的坐标、缩放或 URL 模板。

- 原 Android MapTileProxy 在 JDK17 下请求同一瓦片成功，1,463ms；修复版成功，1,208ms。单次网络耗时不能用来证明修复提速，也不能代表手机的 DNS、VPN、TLS 或 WebView 实际环境。

## 原生请求修复

MapTileProxy 原先即使已有 Content-Length，仍读到连接 EOF。服务器保持连接时，完整瓦片会继续等待或超时。按 [RFC 9112 6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3) 改为按声明长度精确读取，短响应仍报错；无长度和 chunked 路径保留。长度检查拒绝负值、正号与非数字，8MiB 上限、12 秒期限、DNS/IP/TLS 校验及格式校验保留。

旧源码在模拟持续连接中失败于“读超过完整响应体”，修复源码通过；同时覆盖分段读取、尾随字节不被消耗、截断/超限/无效长度、EOF、chunked 和无效图像。该回归证明实现缺陷，不证明手机空白一定由它引起。

## 重采样性能

原 rasterWarp.worker 每个像素创建闭包、索引数组、权重数组并执行多次 reduce。新 rasterResampler 使用标量运算，保留浮点操作顺序、双线性与预乘 alpha、输出像素、尺寸和 PNG 格式；计算仍在 Worker。没有降低清晰度、地图分辨率、DEM tileSize、并发上限或恢复已删除的自动缓存。

测试保留旧循环作 oracle，覆盖 GCJ02/BD09、256/512px、5/9/14/19 级、随机位置、透明/半透明边缘；输出逐字节一致。

主 agent 独立复测：6 轮暖机、21 轮交错、同一 z14 GCJ02 四瓦片 mosaic 的 Node 纯循环中位耗时：

| 输出 | 旧循环 | 新循环 | 加速 |
| --- | ---: | ---: | ---: |
| 256px | 7.38ms | 3.24ms | 2.28倍 |
| 512px | 25.77ms | 11.35ms | 2.27倍 |

这仅证明重采样循环耗时减少约 56%，不代表完整瓦片下载/解码时间、手机 FPS 或奥维同机对比。Luna 的另一轮结果为 2.39–2.51 倍，受电脑负载影响，不作为固定承诺。

## 图库升级迁移

defaultSeeds 保持原数组解析 API，增加含 legacyMapCount 的 bundle；useMapSources 用 bundle 执行初始化。storage 在 IndexedDB 事务前计算与 sameOnlineMap 配置元组一致的 SHA-256 指纹，然后在一个 maps/meta 事务中读取原标记、存档并补缺：旧 value:true 且无新版历史时仅将前 37 项标记已处理，第 38 项只补一次。指纹历史写入原 marker，保留原 key/value:true；用户自建条目、其他 meta、既有 ID 和配置不被覆盖。手动已导入新增源不重复，旧/新增源删除后都不复活；容量或事务失败保留旧数据与标记。

发布前提：私有 manifest 前 37 项必须保持 0.2.94 身份与顺序，只在后面追加；代码按 legacyMapCount 迁移，不会替发布脚本验证旧前缀。本轮与 ignored 合并前备份逐项 JSON 对比一致。独立 9181 origin 的真实 IndexedDB 验证旧标记升级、并发初始化幂等、用户数据保留、删除后不恢复通过，未访问或清理用户 9174/手机数据库。证据 artifacts/screenshots/map-source-seed-upgrade-20261001.png；测试 origin 的合成数据保留用于追溯，测试再次运行遇已有数据库会停止。
