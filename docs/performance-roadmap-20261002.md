# 使用流畅度优化方向 · 2026-10-02

用户要求后期以使用性能和流畅度为主要方向。以下来自当前代码检查与已有局部基准，不把浏览器或序列化测试当作 Android 帧率验收。

## 优先顺序

1. 双图拖动和编辑：检查 `TerrainMap` 的逐帧视角发布、React 更新与 `MapComparisonHost` 的双向同步。地图镜头保持实时，仅合并重复的业务 UI 发布；手势结束立即刷新。现有相邻段几何补丁继续保留。先记录同一手机、同一线路的 p95 帧间隔与长任务，确认卡顿是否来自主线程。
2. 大量标记：`AnnotationLayer` 缩放时遍历 DOM 标记，重建中的 `items.some` 会随数量增加。优先用 ID 集合和呈现状态差异减少重复扫描/DOM 写入。用 0、100、500、2000 标记分别比较同步耗时，验证选择、显隐、模型与移除语义。
3. 路线分析和图表：`routeAnalysis/metrics.ts` 与 `useRouteDisplay` 的速度、坡度、累计距离存在重复分析和数组分配。按几何及分析身份复用一次计算，核对缺测、分叉、反向和窗口边界。不得改变已保存的颜色、透明度或路线顶点。
4. 图源请求：先测双图相同 URL 的重复请求、队列等待及 ArrayBuffer 复制量，再决定共享请求协调。保留取消隔离、不同源/坐标系和私有配置边界，不扩大缓存或修改现有离线数据。
5. 勘探线平剖图：本轮加入地图已加载 DEM 对网络缺测的补充。后续测量 257×49 网格采样/解码耗时；若需要批量地图高程适配，保持同样的有效值、缺测与来源说明。

## 已有证据与限度

- 双图编辑局部负载基准（两图、10000 顶点、120 次更新，五次中位数）序列化耗时从 273.21 ms 降为 3.95 ms，传递顶点从 2400000 降为 30720。这证明相邻段更新减少 JS 负载，不能证明真机 GPU、触控或整体帧率。
- 当前结构中上述路径仍有重复工作机会；尚未对每项录制 Android CPU/GPU 轨迹，因此它们是优先排查方向，不是已经确认的瓶颈。
- MapLibre DEM 的 256 tileSize、影像分辨率与地图视角保持；不通过降低清晰度、减少真实路线节点或取消海拔透明度来换速度。

## 每轮验收

固定同一 Android/WebView 版本、图源、区域、缩放与俯仰，覆盖主图拖动、双图拖动、节点拖动、框选、图源切换及大标记集。记录 p50/p95 帧间隔、超过 16.7 ms 的比例、长任务、首次清晰地图时间、请求队列、内存和温升。每次只改一个已测热点，比较前后并保留操作、存档和画质回归。浏览器定向测试与实际手机性能分别记录。
