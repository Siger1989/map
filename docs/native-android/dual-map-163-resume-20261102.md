# 手机163双图卡顿：暂停后继续调查

用户要求先确认原因、实测改善再交安装包。本轮不提升版本，不替换固定私人163 C14，不发布含凭据安装包。专用 MuMu3 用于隔离诊断，不能代表手机163已验收；Unreal、用户数据和已注册天地图保留。

## 证据与排除结果

- C23 在关闭右侧预览录屏编码、ART采样和QA周期采样后仍有长帧，不能仅归因预览开销。
- 低频子树快照中，主图432组，副图165→166组，容量500组；采样窗口相同key的子树实例替换为0。因此该视角没有证据支持“子树缓存太小导致反复淘汰”。快照本身有开销，不用作性能基准。
- 主线程栈捕获 `BoundingBox.setToSector`，据此隔离实验 C24：当地形更新时间变化、实际高度范围未变时复用包围盒。10项真实SDK数值/失效测试通过，但C23→C24→C23实测无稳定整体收益，**C24不接入活动SDK，不交付**。
- C23/C24系统trace中，一些长帧同时出现主线程等待内存回收、large-object/mark-stack锁；另一些等待没有充分归因。不能把整个睡眠时间或后台GC重叠都记成主线程GC暂停。
- 新C23双图堆快照：970,622个实例、462,148个数组，float数据96,936,188字节（约92.45MiB），byte数据53,749,487字节；大float数组的回溯主要到 `MvtBatchedLineTile.tileData`。这是GC后的驻留快照，排除了数组头/对齐，也会漏掉瞬时垃圾，不是峰值或完整dominator分析。

## C25：减少按图层重复的无用解码（整机仍未通过）

SDK `MvtVectorLayer.loadTileContent` 为每个样式图层完整 `MvtDecoder.decode` 后才应用样式。共享原始PBF缓存避免了同key重复下载，却没有避免道路、路名、地名分别创建不需要的几何和属性对象。

本轮在三个固定规则图层进入SDK解码前，只保留其样式使用的图层内容。保留图层的原始字节完全不变；其余图层留下名称、版本、extent与未知字段，维持SDK schema探测。原始共享缓存和吸附观察者仍取得完整PBF；不减少道路精度、不改颜色/宽度、不减少地名、不关闭双图缓存。自定义样式的陆水层仍完整解码，未知注入源保持原契约。格式异常时回退原始字节。

公开OpenFreeMap z8样本122,830字节，原有陆水/道路/路名/地名四遍解码，与一遍完整加三遍按层筛选对照。真实SDK逐项比较层顺序、schema、feature id/type、geometry、tags与属性一致。JVM预热后交替六轮，每轮100次：

- 原四遍解码：约4,253,848字节临时分配/组，约2.39–3.20ms。
- 筛选加解码：约2,101,800字节/组，约1.13–1.16ms。
- 这仅证明该样本解码工作减少，**不是Android速度或双图修复结论**。

实现模块：`NativeMvtLayerPayload`、`NativeMvtLayerSource`、`NativeCartographyLayers`；增加协议边界、数据完整性、源缓存/条件请求/释放契约测试。C23的Trace诊断与QA只读快照保留。原始trace、堆、APK、mapping仅在`.openai/native163-p0/`，不上传私人内容。

34项/5组定向Kotlin测试、optimized构建、原签名、1925份资源及本机私人天地图一致性、CRC/16KiB审计通过。C25内部包SHA256 `8dcbba6b07ee76f14535076c7c753c0d450a2b1f3bbdc2064763b0c65fdc4a09`，仍为163/code170，未替换固定APK。普通构建使用原始SDK2.1.1，已查mapping确认未带入C24包围盒实验。

## 加载清晰后拖动：新增证据与C26隔离候选

用户本轮明确：手机163两图都加载清晰后，拖动仍很卡，因此入口加载测试不足以关闭问题。所有下述数字来自专用MuMu，非手机验收。临时mask只用于归因，测试结束恢复，不是删除图层的产品修法。

- 预加载稳定后四次小幅拖动：全图层主/副准备202/53次；关闭文字200/44次；关闭MVT207/60次。副图准备明显减轻，但帧数差异不能直接解释为同步丢失。
- 新增计数探针区分重复帧与真实相机变化。四次150 CSS px大拖动，全图层主图155条renderFrame中136个不同相机，副图收到136条命令返回、绘制回传138条；没有发现主图到JS或相机命令漏传。较小手势存在更多相同相机的正常过滤，撤回“约四分之一副图帧数即同步故障”的推断。
- 全图层8.906秒输入窗口，主线程CPU约4611ms、runnable约983ms；SDK准备主330次、副271次。副图路名/地名布局合计约2423ms（嵌套render/labels不可重复相加）。关闭文字后主线程CPU约2353ms，但输入窗口仍8.5秒；QA同步输入有自身开销，不能拿命令用时当FPS。下一步优化重复布局工作，不删除注记。
- 确认普通双图浏览`annotationPicking=true`误触发realtime ground work。临时仅改该flag后DEM路径减少，但四次大拖动9.047秒、相机回传最大间隔仍573ms，尚不足以证明卡顿得到改善。独立纯策略草案留在`.openai/native163-p0/ground-policy-proposal/`，未并入生产修法。
- C26候选改为在已有真实RenderContext准备时捕获metadata，并由该帧GL witness回传；33ms节奏及最终dirty尾采样保留，避免GL画完后为取相机再请求一帧。相同witness只回传一次；pause/resume重新标dirty，销毁清除常驻监听。尚在构建/验证，不是已证明修复。
- 为独立比较C23/C26，已断开C25的样式payload筛选接线；C25文件及测试和其原始接线备份保留。C26不含C24 SDK实验，不改图源/缓存/画质，不升版本，不替换固定163。
