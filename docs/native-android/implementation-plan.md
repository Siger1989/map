# 原生 Android 施工与工作量草案

日期：2026-10-27。用户已确认开始施工；最终替换仍须通过阶段门禁。

## 1. 建议技术栈

| 部分 | 草案 | 选择理由/待验证点 |
|---|---|---|
| 应用/UI | Kotlin + Jetpack Compose，必要时原生View嵌入 | Android原生界面；复刻既有主题和业务行为，不照搬网页运行时 |
| 系统能力 | 现有Java服务重用 + Kotlin适配 | 保留定位、采样、记录、相机、文件、分享；拆除对JS回调的耦合 |
| 数据 | Room/SQLite + 应用文件目录，少量设置用原生持久化 | 事务、版本迁移、附件与业务对象分离；不能直接让Room读取旧IndexedDB |
| 网络/缓存 | 统一原生图源适配与有界队列、HTTP缓存、显式离线包 | SDK的网络扩展接口必须先验证；不能选完引擎再发现无法控制天地图请求 |
| 地图/3D | 支持自有影像、DEM、贴地矢量、模型与拾取的原生引擎，P0后锁定 | 引擎未确定；关键是实际能力覆盖，不以SDK名称相近判断兼容 |
| 算法/格式 | Kotlin为主；确有需要的成熟C/C++库经JNI接入 | 保留测试样例与数据契约，不把JS VM替代WebView当作已经完成全部原生化 |
| 导出 | 原生Canvas/矢量序列化/原生编码与系统文件接口 | 保留现有SVG、PNG、表格和归档结果；不依赖浏览器截图 |

原生地图与天地图服务分别封装。UI不直接拼接私人URL；图源适配层负责鉴权、投影/瓦片行列、范围/级别与缓存身份。导航规划与地图渲染分离，替换引擎不会自动替换已有求路服务。

## 2. 地图引擎第一阶段必须回答的问题

MapLibre Native可以作为二维/瓦片生态候选，但官方terrain支持表目前明确缺少Android/iOS三维地形，不能承诺直接承接当前山兔全部功能。

优先对比两类方案：

1. 已具备原生三维GIS能力的SDK，例如SuperMap iMobile、ArcGIS原生SDK系列：验证具体版本、Android支持、私人天地图WMTS、自有DEM转换、双图、模型遮挡、地质矢量、离线与网络接管。官方宣传存在三维能力不等于这些组合已兼容。商业授权、离线部署、数据格式/服务限制和费用须取得明确资料后再决定。
2. 开源原生地图加专门的原生3D渲染实现：可保持更多控制，但须承担地形LOD、接缝、拾取、贴地线/文字/模型、深度遮挡、坐标精度与双图资源管理。不是简单增加一个3D插件。

Mapbox等候选也不能只凭“支持terrain”判定合格；其Android文档目前对Raster DEM源有提供方限制，自有DEM与现有许可范围是独立门槛。

验证场景使用用户许可的隔离测试数据：
- 内置天地图影像/矢量/注记正常出图，原生Key使用方式有效，敏感参数不入日志。
- 山体显示真实高度；自有地形与影像正确贴合；缩放旋转无明显裂缝。
- 一条跨山脊路线、前后各一个标记、一张照片、一个模型：贴地/遮挡/选择行为正确。
- 双图同时打开、相机联动、切换图源不跳zoom；测得内存与持续交互帧时间。
- 断网、延迟、429、恢复网络后补图；失败诊断可分辨图源/地形/文字。
- 解码一份当前支持的DWG和一份行业模板，证明纯原生替代管线可行。

全部通过才锁定SDK和更新工期。如果只有二维成功，应标为验证未通过，不能以删掉三维或偷偷退回WebView推进。

## 3. 阶段与依赖

以下为工程估算，不是已承诺日期。人日指一名熟悉相关领域的工程师一个有效工作日；含开发与该阶段定向验证。SDK采购、账号等待、用户设备等待另计。第一阶段后重新估算。

| 阶段 | 具体工作/交付物 | 人日范围 |
|---|---|---:|
| P0 功能基线与技术验证 | 完整入口矩阵、数据样例清单、地图/3D/网络/关键格式原型、引擎比较和决策记录 | 15–25 |
| P1 原生基础 | 应用工程、主题/导航/状态、数据库、日志脱敏、系统服务接口与迁移框架 | 15–25 |
| P2 地图底座 | 天地图/现有图源、真实地形、地名/道路、相机/双图、浏览缓存/离线包、超时/限流/恢复 | 35–60 |
| P3 户外核心 | 定位/记录/导航/返航、路线分析、画线/吸附/区域/测量及全部状态规则 | 35–55 |
| P4 对象与交换 | 收藏/标记/照片/模型交互、文件格式、工程JSON、坐标交换、主题和布局 | 35–55 |
| P5 专业工具 | 剖面/测点/地质、CAD参考层、行业Excel/钻孔/剖面、原生图表和导出 | 45–80 |
| P6 替换验收 | 数据迁移往返、长后台/弱网/压力、功能矩阵回归、原签名覆盖安装、修复与交付 | 25–45 |
| 基础合计 | 假设现成原生引擎通过P0，不含自研完整地形引擎 | 205–345 |

预留约25%的兼容和返工量，当前预算取整为 **260–430人日**。这不是报价或测量值，源于本仓库功能组规模、原生渲染/数据迁移风险和已有Java复用边界。

若需要较大规模自研地形渲染，另外暂留 **80–160人日或更多**，P0后才能细化；不得把它藏进普通界面工期。

以两名有Android/GIS经验的全职开发、另有测试协助为参照：
- 约3–6周：得到可装手机的原生地图验证版，说明哪些能力已经验证。它不是日常替代版。
- 约3–5个月：有望形成地图/记录/路线/基础收藏等日常功能试用版，专业功能可能仍在迁移。
- 约8–12个月：现成引擎路线下完成上述全部范围并收敛真机问题的初步排期；外部等待与引擎失败可延长。
- 单人完整推进约13–22个月量级；增加人员受接口、引擎和设备验收依赖限制，不能简单按人数相除。

AI可帮助移植、生成界面、构造测试和审查，但以上不直接换算为AI运行时长或额度消耗。不能在没有P0证据时承诺几天完成全部迁移；每阶段按实际完成与返工情况修正剩余估算。

SDK/商业DWG库许可、开发者账号、设备与第三方数据费用未包含在工时中；本轮未购买、未询价、未承诺固定金额。

## 4. 数据迁移与切换

1. 保留当前源码和141私人包作为基线；原生研发使用独立模块/分支，测试安装身份隔离，最终是否替换由门禁决定。
2. 先以旧版导出的完整工程/旧备份复制件建立迁移样例。原用户存档不作为破坏性试验对象。
3. 原生导入以事务写入，核对数量、ID、几何、时间分段、附件哈希、图源/CRS和设置；不支持字段原样保留或明确阻断，不能静默丢弃。
4. JSON不含的缓存包、草稿、后台暂存、外部文件权限逐项迁移。必要时制作独立过渡导出方案，不能让最终原生版本依赖旧WebView读取数据。
5. 测试新旧导出往返；部分原生新增字段可以命名空间扩展，但旧版兼容性需明确。降级安装不是回滚保障，回滚依靠预迁移备份和可读交换文件。
6. 真机通过后用原包名/原签名做覆盖迁移验证。此前继续保留原应用及历史包。

## 5. 协作与后续平台

用户确认施工后，按项目规则将网络缓存、存储迁移、格式算法、独立UI等边界清楚的任务交低消耗子agent并行；同一地图引擎适配文件不多人同时修改。主agent负责接口、整合、真实证据复核。此安排不能替代GIS引擎验证和真机验收。

Android完成后，业务schema/测试样例/部分C++算法可给iOS、HarmonyOS和桌面复用；各平台原生UI、后台能力、地图SDK、签名与安装单独规划。原Mac140仍是WKWebView地图加原生系统能力，不能称已完成本次全原生目标。
