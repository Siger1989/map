# 手机163双图卡顿复查（2026-11-02）

用户已明确：问题发生在手机163，双图仍非常卡。该版本双图真机性能为 **FAIL**；此前模拟器无崩溃和静止收敛不能覆盖此反馈。固定私人APK保持163 C14，未用诊断包覆盖。

## 新证据与原因边界

- 专用MuMu3上的163 C14补测普通远景双图，地形打开，等高线开关打开但当前级别生成批次为0。双图两轮操作约32.3秒，主、副地图瓦片需求重算累计墙钟分别增加约3.437秒和1.143秒，合计4.58秒。整个流程有效Java采样峰340.24MiB/512MiB，主线程可用样本最大317ms，另一次主线程快照超时。这说明这类开销可以在没有等高线生成、内存未顶满时出现；不是手机性能数值，也不是纯CPU时间。
- 另一次显式开启诊断栈采样，共733次快照。145份主线程栈包含`refreshTileDemand`，其中107份来自绘制后的回调，38份来自`applyRenderState`。源码确认后者无条件调用不带实际MVP的排序；前一帧签名含MVP，而该路径签名不含MVP，因此重复排序，并回到逐角点SDK相机变换路径。
- 高频采样自身平均耗时16.11ms，最大540.64ms，存在观察扰动；它只能用于定位调用路径，不能据此报告FPS或优化前后速度。正式前后对照关闭高频栈采样。原始栈、坐标和截图仅保留本机`.openai/native163-p0/feedback-*`。
- 近景等高线场景原有503.86/512MiB峰值与GC阻塞问题仍未关闭。本轮发现不表示内存问题不存在，也不证明已经找到手机上全部卡顿原因。

## 已实施的调度修复，仍在验证

1. 普通业务状态更新不再立即执行无MVP的全量角点换算，使用实际绘制帧。
2. 只合并连续相机运动中的加载排序计算，保留最新MVP/视口，并保证停手后的最后一次更新。真实新瓦片、图源或可见性变化不能丢失；隐藏地图立即停止其前台需求。
3. 不更改地图绘制帧率、图源清晰度、20个下载并发槽、中心优先排名算法或8GiB磁盘缓存。

纯相机排序采用100ms最短间隔，合并为最新实际MVP，定时尾任务不依赖后续新帧。它不是绘制帧率限制，也不是下载限速。真实新增瓦片、图源/可见性变化走紧急通道；不使用过期视口MVP。未变化的道路/注记可见性设置不再重复触发排序。

### C14 → C15 → C16原生诊断对照

专用MuMu3、相同远景初始相机/手势脚本/设备分辨率，两轮双图操作；天地图卫星影像与开源道路地形。高频栈采样关闭，原生预览采集持续运行。两次都由磁盘/内存缓存供图，网络请求为0；等高线开关打开，但级别低于生成范围，完成批次为0。

| 两轮双图操作 | C14 | C15 | C16 |
|---|---:|---:|---:|
| 操作总墙钟 | 30.269s | 22.181s | 25.772s |
| 主副图需求排序累计墙钟 | 10.819s | 2.701s | 2.171s |
| 重排次数 | 776 | 249 | 253 |
| 可用主线程派发延迟P95 | 206ms | 104ms | 196ms |
| 可用主线程派发延迟最大值 | 251ms | 142ms | 270ms |
| 有效Java采样峰 | 469.99MiB | 505.69MiB | 470.15MiB |

这是一组原生诊断对照，不是手机FPS、下载速度或严格隔离的因果基准。JIT/缓存解码时间存在差异，不能把总操作时长变化全部归因于本次改动。排序重复工作下降有直接计数支持；手机163性能仍FAIL。

排序计数窗口为双图ready快照至第二轮after快照；延迟/heap窗口为dual-active至dual-idle标记。C16补道路样式快照后，整体停顿没有稳定减少，不能把理论少分配写成已验证的整体性能收益。三次主副原生帧均实际推进，结束时网络active/queued均0。

C15的37项/6组定向Kotlin测试、optimized构建、原签名/非debuggable/CRC/16KiB对齐通过。应用资产、私人天地图配置和本机库与C14逐字节一致，只有DEX优化profile随构建重生成。C15只安装专用模拟器，未替换用户固定APK，也未作为新版本交付。

C16的47项/7组定向Kotlin测试与optimized构建通过，相同完整性审计通过，已核对专用模拟器安装SHA256为`842a4049af08b0fdc844544c6558ee43b2990a046eb44b6e8073f0441dced909`。仍为163/code170内部诊断，不是新交付版本。首次单独运行apksigner审计因该shell未设置JAVA_HOME失败，设置已有JDK17后审计通过；没有修改签名或降低检查。

### 仍未解决的内存回收压力

C15实际测试窗口出现主线程等待GC约99.356ms；回收日志显示大量短期对象和大数组释放。505.69MiB采样峰不等于已发生OOM，GC后存活量更低，但操作线程被阻塞是实测缺陷。

另一次双图堆快照中，普通MVT线条几何是大块float数组的重要持有者；229个不小于64KiB的float数组中，相同字节内容的额外副本合计约34.75MiB。相同内容可能来自同一图窗道路描边/填色，尚未归属到具体图窗，不能直接称为主副图重复缓存。堆快照会触发GC，不能替代瞬时分配或性能测量；原始堆、坐标和日志仅保留本机。

补充窄修复：道路每瓦片每帧重新计算宽度/透明度会创建插值Pair、装箱数值和样式对象。现在把各组样式放在每图窗独立的视角快照中，只有有效zoom/CSS scale改变才重新计算。显隐阈值、宽度/颜色、几何精度与缓存保留。此项减少已确认的重复分配，但尚不能证明已消除整体GC压力。

### C16近景等高线与关闭副图复测

同一专用模拟器两轮真实旋转/倾斜/平移/缩放操作24.329s，主线程派发延迟P95为203ms、最大339ms，无主线程快照超时；整个测试有效Java采样峰501.39MiB/512MiB。这仍不满足整体流畅和内存余量要求。

双图静置120s，每20s六次快照均为completedBatches35、共享几何34项/63 leases，网络active/queued为0；没有该窗口内反复生成/排队的证据。关闭副图20s再静置60s后为1map、共享几何32项/32 leases，副图的等高线lease已释放。不能据此推断所有类型内存或所有场景都无问题。

随后恢复初始相机（经纬度/zoom/pitch/bearing模360核对），标记数量一致、回单图、原生交互服务ready，物理1256×2760/density515未变。测试没有画线、删改标记或清缓存。用户固定C14包继续保留。近景长时/手机性能仍未验收，不称P0已修完。

## 下一步工程边界（尚未实施）

普通MVT当前在低zoom也构建所有道路组，随后才跳过不可见组；可评估按当前可见组延迟生成几何。必须保留SDK resident tile和已建组，不能通过反复invalidateTile换取内存，否则可能引入新的缺图/闪烁。候选设计为每tile包装对象：初建当前可见组，后续缺组通过有界后台任务补齐；成功才释放对应未建源子集，eviction/close取消任务并释放几何。需要证明与SDK装配任务并发安全、释放GPU的线程/上下文正确、失败有界退避、关闭时不被晚到结果复活。高zoom最终仍需完整几何，不预先承诺总内存降幅。未经这些验证不接生产。
